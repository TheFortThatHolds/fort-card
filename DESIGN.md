# Fort Wallet — design (source of truth)

A standalone, self-hostable credential wallet for the agent era. It **works entirely on its
own** and can **plug into the Fort Memory Core (FML)** as an optional control plugin. This doc
is the agreed shape; code follows it.

---

## 0. The anchor rule — standalone first, plugin second

- The wallet is a **separate app**. It runs, deploys, and is used **without the Core**.
- FML integration is a **thin plugin** on the *Core's* side that calls the wallet's API
  (issue a card, approve, rotate) from the FML surface. The plugin **holds no keys** — it's a
  remote control, not a dependency.
- **Hard rule: the wallet has ZERO dependency on the Core.** Delete the Core and the wallet
  still works. The Core just loses a remote.

Two modes:
- **Standalone** — deploy the wallet, use its API / its own PWA. No Core. Approvals (and all
  controls) happen in the **wallet's own PWA**.
- **Plugged-in** — FML loads the control plugin and drives the wallet remotely. The concrete
  difference for you: **the approval surfaces inside FML instead of the wallet app**, so you
  approve where you already are without switching apps.

**The plugin is glass, not authority.** Even when you approve *in FML*, FML only *shows* the
pending card and *triggers* the passkey tap — the **wallet still verifies your passkey and
flips the card live**. FML never becomes a second approver that can say yes on its own, and it
never holds a key. Same cryptographic gate, different screen.

## 1. Multi-tenant — spaces born from identity

- One deployment hosts many tenants. **Every** record (secret, card, statement, data key) is
  walled behind a `space:` prefix — the hard isolation boundary.
- **A space does not exist until a verified identity calls it into being.** Sign in → verify →
  the space is born (its DEK minted, its records begin). Nothing is addressable before that.
  Kills space-squatting, enumeration, and pre-provisioned attack surface. Existence = proof.
- **Space id = the provider's immutable numeric id** (`github:<id>`), never username/email
  (mutable → takeover). **Server-derived only — never from a client header/param.**
- Self-host stays single-tenant for free: one space, never a second.

## 2. Identity — GitHub App, zero repo permissions for auth

- One **Fort Wallet GitHub App**, used via the user-authorization flow for identity. It needs
  **no repo permissions to authenticate** — the install/permissions step is skipped for login.
- The *same* app can later — *only with the user's grant* — provision/manage the user's
  **private vault repo** (GitHub as trust broker). Auth today, vault-repo tomorrow, one spine.
- Hardening: `state` param (CSRF / code-injection), exact callback-URI allowlist, validate the
  identity, use the immutable id, **never link accounts by email**.

## 3. Human auth — banking-app model, every time

- **Every sensitive human action requires a fresh fingerprint / device PIN** — WebAuthn passkey
  with `userVerification: "required"`, *each time*. No lingering session, no "already did it
  once on this device," no remembered unlock.
- Tap-every-time actions: open the vault, view a secret, issue/approve a card, rotate the key,
  **mint an agent bearer**.
- **There is no long-lived human session anywhere** — so there's none to steal.

## 4. Agent auth — scoped, delegated, revocable bearers

- The human (with a tap) **mints an agent bearer**: agent-tier, **hashed at rest**, **TTL'd**,
  **revocable**.
- An agent connects with the bearer (MCP / env, like any API key) and runs **autonomously,
  no fingerprint** — because the human *already* signed its scope when minting it.
- Agent bearer **can**: use cards within caps, freeze, revoke. **Cannot**: issue a card,
  rotate, store a secret, or reveal a raw key.
- Worst case from a stolen agent bearer: spend inside caps you already set. Never escalation,
  never raw keys, never your other secrets.

## 5. Two-tier secrets — you choose, per secret

- **Autonomous** — the host can settle it for your agents while you're away (per-space DEK under
  the master KEK). Convenient, headless, **custodial** (host can decrypt).
- **Sovereign** — sealed to your passkey via WebAuthn **PRF**. **Host-blind** — opens *only*
  under your live tap. **No autonomous use.** Maximum sovereignty.
- Honest custody truth: **hosted = you trust the operator** (the KEK unwraps autonomous
  secrets). **Sovereign self-host = you are the operator.** Sovereign-tier secrets are
  host-blind regardless of who runs it. A wallet whose autonomous job is to charge a card while
  you sleep *must* be able to decrypt while you sleep — that's physics, not a gap.

## 6. Key authority — generate freely, authorize as the owner

- **KEK** = `MASTER_KEY`, a deploy secret, the sovereign root. **Never rotated in-app, never
  generated by an agent.** Born in the owner's hands, lent to the worker.
- **Per-space DEK**, wrapped by the KEK, **rotatable by the owner** (a tap) without touching any
  other space.
- Rotation re-seals the space's secrets under a fresh DEK. The KEK never changes → a rotation
  **can never lock the owner out**, and an agent token **can never re-key**. Backward-compatible:
  secrets with no `keyRef` open under the KEK, so rotation is opt-in.

## 7. Cards — the everyday primitive (per space)

- A card = a **scoped, capped, freezable pointer** at a secret. The agent gets a card, never the
  key. Charge: agent presents `card + request` → wallet checks rules (frozen? expired? over
  limit? host allowed? **+ SSRF block** on private/link-local/localhost) → injects the key
  server-side → returns only the response. Credential header injected **last** so a caller can't
  strip or override it.
- Issue / approve = owner act (a tap). An agent-requested card lands **pending** (inert) until
  the owner approves.
- Caps are **best-effort under concurrency** (KV has no transactions); a hard cap needs a
  Durable Object. Stated, not hidden.

## 8. Approval + wake — GitHub, the user's own repo ONLY

- Agent requests a card → **pending** → owner notified (**push-first**, per-user toggle).
- Owner approves **in the wallet** (a tap) — the wallet is the primary approval surface.
- The **continue / wake signal** posts to the **user's OWN repo** (where the agent works / their
  app installation) — **NEVER the public `fort-card` repo.**
- The **public repo is code-only — a one-way valve.** It never receives a runtime write
  (approval, request, event, secret). Enforced by the GitHub App **installation boundary**: the
  token can only write where the user installed it, which is never the public template.

## 9. Public code, private vaults

- The wallet code is **public** (auditable, forkable). **Keys never live in any repo** — public,
  private, fork, or duplicate. They live in each deployment's **Cloudflare** (KV + Worker
  secrets).
- Each user either **runs their own deploy** (their keys, their Cloudflare — full sovereignty)
  or is a **tenant on a hosted instance** (the custodial trade, eyes open).

## 10. Split deploy — the last mile on your own infra (the managed-without-custody answer)

The custody truth in §5/§9 says "hosted = you trust the operator, because the operator's worker
holds the KEK and decrypts your autonomous secrets." A **split deploy** removes that trust from
the *managed* path by separating the **last mile** (decrypt + inject + fetch) into its own worker
that runs on **your** Cloudflare and holds **your** `MASTER_KEY`.

- **Control plane** (`src/worker.js` with `LAST_MILE_URL` + `LAST_MILE_KEY` set) — the managed
  service. Holds **only ciphertext**: sealed secrets, KEK-wrapped DEKs, cards, the statement. It
  has **no `MASTER_KEY`**, so it **cannot decrypt anything**. On a charge it relays the sealed
  secret to the last-mile worker and returns the response. It runs the wallet, approvals, audit —
  the whole UI/orchestration — while being **plaintext-blind**.
- **Last-mile worker** (`src/last-mile.js`) — thin, **stateless**, on *your* account. Holds
  `MASTER_KEY`. One job: open a sealed secret, inject it into one outbound call (credential header
  **last**, **SSRF-blocked**), return the response. No cards, no storage, no UI. The plaintext key
  exists only here, only for the duration of one fetch, only on your infrastructure.
- **The envelope is identical** on both sides (AES-256-GCM, per-space DEK wrapped under the KEK),
  so seal/charge/rotate are cross-compatible. The control plane delegates `/secrets` (seal),
  `/use` (charge), and `/rotate` (re-seal) to the last mile; **drop its `MASTER_KEY` entirely**
  once `LAST_MILE_URL`/`LAST_MILE_KEY` are set.
- **Unset = single-worker self-host**, decrypt inline — the original behaviour, unchanged. The
  split is purely additive; nothing existing regresses.

This is the offering: **fork-and-self-host** (one worker, you operate it) OR **managed control
plane + your own last-mile worker** (we run the wallet, your keys never leave your Cloudflare).
Cryptographic, not pinky-promise: no `MASTER_KEY` on the operator's box → no plaintext on the
operator's box.
